# Доступность, выпуск и восстановление

[Обзор проекта](../README.md) · [Проверки](QUALITY.md) · [Развёртывание](../DEPLOYMENT.md)

## Что проверено 2 ноября 2026 года

Во время обращения о временной недоступности главная, форма входа, `/health/`, сервис КР и календарь отвечали. В просмотренных журналах за три часа не было перезапусков, аварийного завершения из-за памяти или ошибок PostgreSQL. Причину недоступности примерно за час до обращения установить по этим данным нельзя.

При этом воспроизведена отдельная ошибка HTTP: приложение возвращало HTML-тело на HEAD главной и формы входа. Waitress передавал его прокси, который регистрировал неожиданные данные в постоянном соединении. Исправление сохраняет заголовки GET, но исключает тело HEAD, включая потоки и файловые ответы. Проверка обращается к настоящему WSGI-обработчику: обычный тестовый клиент Django скрывает такую ошибку, удаляя тело самостоятельно.

Также исправлена блокировка редактируемого шага курса в PostgreSQL: `FOR UPDATE OF` применяется только к самому шагу, без nullable-стороны соединения с родителями. Проверки резервирования выполняются с зафиксированными данными, вне внешней тестовой транзакции. Рабочая копия PostgreSQL по-прежнему создаётся в транзакции `REPEATABLE READ READ ONLY`; вложенный запуск явно отклоняется вместо создания несогласованного снимка.

## Ежеминутная проверка сервиса

[`watch_service.py`](../deploy/watch_service.py) запускается на Ubuntu через systemd. Он проверяет состояние контейнеров и `/health/` через локальный HTTPS-прокси с проверкой настоящего сертификата домена.

- Три последовательные неудачные проверки нужны до восстановления.
- Зависший контейнер приложения перезапускается, только если PostgreSQL исправен.
- Прокси перезапускается при устойчивой ошибке соединения или ответе 502/503/504, если приложение исправно.
- Между попытками восстановления одного сервиса проходит не менее 15 минут.
- База данных автоматически **не перезапускается**. Остановленные вручную и ещё запускающиеся контейнеры не считаются зависшими.
- Маркер `/opt/infocode/.deploy-in-progress` при занятой блокировке выпуска приостанавливает восстановление и сбрасывает счётчик ошибок. Оставшийся после аварийного завершения маркер без блокировки не отключает проверку навсегда.
- Ошибки сертификата фиксируются, но не вызывают бессмысленный перезапуск прокси.
- Журнал содержит состояния и выполненные действия, без паролей, токенов и содержимого запросов.

Проверить работу:

```bash
sudo systemctl status infocode-watchdog.timer
sudo journalctl -u infocode-watchdog.service --since '1 hour ago' --no-pager
```

Перед длительными ручными работами остановите таймер, после — запустите снова:

```bash
sudo systemctl stop infocode-watchdog.timer
# Плановые работы администратора.
sudo systemctl start infocode-watchdog.timer
```

Локальная проверка не подтверждает доступность через сеть каждого ученика. Для контроля внешнего DNS, маршрута и площадки нужен независимый внешний мониторинг; на самом VPS обнаружить потерю всего VPS невозможно. Автоматическая проверка не заменяет копии вне сервера.

## Выпуск правок без изменений схемы базы

[`release.sh`](../deploy/release.sh) рассчитан на существующую установку `/opt/infocode`. Запускается из проверенной копии исходников на Ubuntu от администратора:

```bash
sudo bash /путь/к/проверенной/копии/deploy/release.sh /путь/к/source.tar.gz
```

Архив содержит файлы проекта относительно его корня, без рабочего `.env.production`, БД, моделей нейросети, пользовательских загрузок и секретов. Сценарий проверяет пути до распаковки, исключает параллельные выпуски через `flock`, собирает новый образ при работающей старой версии, проверяет настройки приложения и Caddy.

Если есть неприменённые миграции, выпуск останавливается: такие обновления требуют отдельного плана изменения схемы и основной инструкции развёртывания. Сценарий создаёт проверенную копию базы и файлов, сохраняет прежние исходники и идентификатор образа. Затем обновляет только приложение и обслуживание, проверяет содержимое и HTTP, устанавливает таймер.

Если после переключения возникает ошибка, сценарий пытается вернуть прежние исходники и образ. Это **откат кода**, не восстановление базы: новые ответы учеников не удаляются. Исходники находятся в `/opt/infocode-releases/<дата>/previous-source.tar.gz`, копия данных — в томе резервирования под именем `before-release-<дата>.zip`. Три последние копии данных выпуска сохраняются; старые удаляются только после успешных проверок нового выпуска. Дневные и вручную названные архивы этот сценарий не удаляет.

Сам сценарий следует запускать через `nohup` или `systemd-run`, чтобы обрыв SSH не прервал выпуск. Результат обозначается `INFOCODE_RELEASE_READY` и `INFOCODE_RELEASE_EXIT=0`; иначе проверьте журнал и результат отката.

[`smoke_check.py`](../deploy/smoke_check.py) проверяет главную, форму входа, доступность базы, таблицу стилей и отсутствие тела в HEAD-ответах через HTTPS. Тесты и проверка интерфейса с авторизацией дополняют её, но не заменяются ею.
